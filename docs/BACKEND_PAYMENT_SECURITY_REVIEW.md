# Backend payment and authentication review

**Latest phase-2 implementation:** JWT authorization now uses current DB roles; guest email ownership, arbitrary financial status values, cart stubs/invalid quantities, public review email, sensitive logging and broad CORS are fixed locally. Runtime datasource settings are required and schema mode defaults to validate. Full backend suite/package passes 134 tests. [The current report](PRODUCTION_PHASE2_REPORT.md) and [Render instructions](RENDER_SECURITY_RUNBOOK.md) identify remaining concurrency/idempotency/session/collection/hosted work. Older audit findings below are historical, not a deployed attestation.

## Current local patch status — 16 November 2026

A bounded patch is prepared locally for review: runtime-required JWT_SECRET replaces the embedded key; implicit fixed-password/admin and initializer schema/role-repair SQL are removed; explicit local bootstrap requires supplied credentials and is excluded by production/prod profiles; User passwords are excluded from JSON and Lombok logging. Dedicated tests cover configuration/startup wiring, rotation/invalid tokens, direct/nested serialization, DTO registration and bootstrap behavior. See `Backend/SECURITY_RELEASE_NOTES.md` and the [current consolidated report](PAYHERE_OWNER_RESPONSE_REPORT.md).

The later [fixed-delivery change](FIXED_DELIVERY_IMPLEMENTATION.md) centralizes BigDecimal order pricing, adds LKR 350 to both order paths, rejects empty/nonpositive-quantity/invalid-price orders, and validates combined cart quantities before writes. These bounded order-creation checks do not repair the separate cart-mutation/stub, concurrency, idempotency or ownership findings. No live payment method was enabled.

No deployed credential, session, account, schema or customer record changed. Provision a newly generated server-only key, coordinate rotation across instances and revoke old sessions; reset/disable any existing default-admin accounts. Hibernate ddl-auto=update and the broader ownership/catalog/cart-input/concurrency/CORS/privacy findings remain unresolved. paymentSafetyReviewed remains false. ## Current payment controls

- `Backend/src/main/java/com/cosmetic/ecommerce/service/OrderService.java:118` rejects every non-COD direct order before product lookup, stock deduction or saving. Accepted direct orders use `PENDING_COD`, not `PAID`.
- `dto/DirectOrderRequestDTO.java:30` permits COD only and rejects populated removed card fields and client-supplied payment status. Legacy null card fields are tolerated without retaining their values.
- `controller/OrderController.java:78` calls the response an order confirmation, not proof of payment. Cart orders default to COD / `PENDING`; neither active creation path calls PayHere or assigns verified online settlement.
- No raw card inputs or card payload fields were found in the local frontend checkout. No live PayHere integration or verified provider callback exists. Do not enable live payments simply because COD regression tests pass.
- The current production frontend bundle still contains `cardNumber`, `cardExpiry`, `cardCvc` and `KOKO_APPROVED`, and lacks the new policy route string. These are source-string signals from a public GET, not a live transaction test. The deployed frontend must not be assumed to include the local remediation.

## Release blockers and evidence

| Priority | Finding | Source evidence and implication |
| --- | --- | --- |
| Critical | Hardcoded JWT signing material | `util/JwtUtil.java:15` embeds the signing key; `config/JwtFilter.java:38` accepts signed claims and `:46` uses the claimed role directly. A disclosed key can enable forged user/admin identities if deployed unchanged. No token was forged or used in this audit. |
| Critical | Built-in administrator password | `config/AdminInitializer.java:29` creates an ADMIN with a fixed password when the email is absent. Remove automatic production bootstrap; rotate any deployed credentials through a controlled owner process. Values are deliberately omitted. |
| High | Password hash serialization | `entity/User.java:7` uses Lombok `@Data`; its password has no JSON exclusion. `entity/Cart.java:26` exposes `getUser()` and `controller/CartController.java:34,42,49,59` return raw Cart entities. This provides a source-level response path to a password hash. No customer cart response was requested. `Order.user` already has `@JsonIgnore`; do not claim that relationship is unprotected. |
| High | Guest identity association | `service/OrderService.java:173` falls back to submitted email to link an existing account. A supplied email does not establish ownership; guest orders must not be attached to an account on that basis. |
| High | Invented purchasable products | `service/CartService.java:38` creates a generic product with an invented price and stock when an ID is unknown. This also explains how mock catalog records can recur. Reject unknown IDs; do not silently populate production goods. |
| High | Invalid/combined quantities | `dto/AddToCartRequest.java:3` lacks constraints; CartController does not apply `@Valid`. CartService compares stock with the incoming increment, not the combined line, and accepts invalid quantities. Direct-order quantity silently falls back to one for nonpositive values. These paths need explicit service-level validation. |
| High | Concurrent stock and duplicate orders | Both order flows read/check/save stock without a product lock, version or atomic conditional decrement. Transactions alone do not prevent lost updates. Direct COD lacks server idempotency; frontend one-request guards cannot prevent network retries creating duplicates. |
| High | Startup performs schema/data writes | `config/AdminInitializer.java:18,24` runs ALTER/UPDATE on startup in addition to admin creation. `application.yml` also configures Hibernate schema behavior. Never start this application against production as a diagnostic check. Use explicit reviewed migrations and a controlled bootstrap procedure. |
| Medium | Credential/configuration defaults | `application.yml` and `docker-compose.yml` contain literal database defaults. Cloudinary uses environment references with defaults. Classify development-only values and replace credential-bearing production defaults with required server configuration; audit Git history and rotate any real exposed credentials. Existing Render settings were not accessible. |
| Medium | Overbroad credentialed CORS | `config/SecurityConfig.java:86` allows wildcard origins on multiple shared hosting domains and credentials. Restrict to the approved site and explicitly managed previews. This alone does not prove an authentication bypass. |
| Medium | Long-lived browser tokens and logging | JWT expiry is seven days; the frontend stores JWTs in localStorage. `JwtFilter.java:53` logs account identifiers and roles, and JwtUtil logs exception details. Review token expiry/revocation, XSS/CSP, log minimization and retention. Do not switch to cookies without designing CSRF protection. |
| Medium | Public reviewer email | `dto/ReviewResponseDTO.java:12` exposes `userEmail`. Review responses and frontend rendering need a safe display name/alias instead. |
| Medium | Unrestricted order-status values | `service/OrderService.java` accepts any nonblank admin status string. The endpoint has an ADMIN guard; it does not set `paymentStatus`, so this is not an observed automatic-PAID bypass. Enforce valid fulfilment states and keep financial transitions separate. |

## Separate implementation plan for review

1. **Secrets and bootstrap:** inject a high-entropy JWT key from Render server-only settings and fail startup if absent/invalid. Coordinate key rotation and session invalidation, remove fixed admin creation, arrange a one-time authorized admin-credential rotation, and remove production DDL/data patches from startup. Keep all payment/JWT/database secrets out of `VITE_*`, client bundles, docs and commits. History cleanup and credential rotation are separate reviewed operational actions.
2. **Safe API responses:** add explicit Cart/User response DTOs, exclude password from serialization and Lombok `toString`, and test every cart mutation/read. Replace public reviewer email across backend and frontend. Preserve authentication/principal checks and add owner-vs-other-user authorization tests without real accounts.
3. **Order and inventory integrity:** reject unknown/inactive products, null/nonpositive/excessive quantities, and invalid request fields before mutation. Validate combined cart quantities; remove invented price/stock defaults. Use BigDecimal monetary calculations, approved shipping/tax/coupon rules, and server-calculated totals. Owner fee decisions may require a versioned backend/frontend contract change.
4. **Concurrency and identity:** make stock deduction atomic under competing transactions, roll back all order lines on failure, and add idempotency for order creation. Bind registered orders only to the authenticated principal; leave guest orders unassociated until a separately verified claim. Make guest-order lookup null-safe and owner-scoped. Define allowed fulfilment transitions and audit administrative changes.
5. **Production boundaries:** restrict CORS to configured exact origins, minimize logs, validate authentication inputs, review login/guest-order rate limits, and agree session lifetime/revocation and browser protections. Add a delivery phone to cart checkout only with an agreed DTO/UI migration and fulfillment requirements.
6. **Sandbox payment work, separately:** after the security changes are reviewed, use PayHere-hosted checkout so card credentials stay with the provider. Generate checkout hashes on the server; verify the notification checksum, configured merchant, order, amount, currency and successful status; process notifications idempotently and reconcile retries. Never accept client payment status or treat a return URL as payment verification. Keep live credentials and endpoints disabled until merchant/domain approval and a successful Sandbox review.
7. **Review, staging and coordinated release:** review the diff and migrations; run serialization/authentication, invalid-quantity, combined-stock, competing-last-item, rollback, duplicate-request and provider-notification tests against an isolated database. Reconcile historical simulated payment records with the owner without automatically rewriting them. Review staging logs and deploy the compatible backend before the frontend; independently verify the Render revision. No production migration, credential rotation, merge or deployment is authorized by this document.

Plan review also requires a rollout across every backend instance that stops accepting the old JWT key, and a reset/disable process for existing default-admin accounts: removing bootstrap code does not change persisted credentials. Exercise migrations and startup against an isolated database. Define money precision/rounding and historical-value conversion; stock reservations, expiry, cancellations and refunds; protected guest-order access; and duplicate/out-of-order provider notifications that cannot repeat fulfilment or downgrade an already paid order. Use PayHere's exact documented checksum/amount formatting and verify it before any side effects. Test forged, mismatched and delayed notifications as well as success. These are acceptance criteria for a future implementation, not work completed here.

The developer can implement and test these code changes locally after this plan is reviewed; any production actions remain a separate manual release step. Owner/legal decisions are also required before describing actual data retention, fees or contractual policies as final.
