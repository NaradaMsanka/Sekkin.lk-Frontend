# Immediate credential containment and separate public-sales release

Prepared 16 November 2026. **Instructions for the authorized operator; no production credential, account, deployment or record was changed by this work.** Business/policy approval must not delay containment of previously exposed signing material or administrator access. A secure public shopping launch and an urgent containment release are separate operator decisions.

## Act independently of final policy approval

1. Identify the actual deployed backend revision and every service/instance accepting its JWTs. Treat formerly committed signing material as exposed. Review secret locations/history without printing values; removing source literals does not revoke existing tokens or eliminate historical exposure.
2. Immediately restrict access to compromised authentication/admin/order paths using an existing operator-controlled ingress/maintenance mechanism. If no verified mechanism is available, the operator must select an appropriate temporary service-isolation action. Do not assume a frontend button, draft metadata or a CORS rule prevents direct API access. This workspace has not changed the running service's availability.
3. Review existing administrators and authorized access. Disable/revoke compromised accounts through a verified, compatible administrative procedure; do not guess SQL, delete order-linked accounts or claim that the currently deployed old binary already supports new account APIs. Reset compromised credentials through an approved secure process. Do not send secrets, customer tokens or identity/bank documents in chat.
4. Generate a fresh independent high-entropy `JWT_SECRET` with the nonprinting procedure in [the Render runbook](RENDER_SECURITY_RUNBOOK.md). Never reuse or restore the exposed value. Configure the new key on **every** accepting instance. Replace/drain old-key instances so they cannot continue serving protected requests. Verify rejection of an old controlled staging token and acceptance after a fresh login.
5. If containment requires the reviewed backend, stage the compatible migration and dependency/runtime checks and obtain separate authorization for an urgent backend-only deployment **with ordering paused**. Set `CHECKOUT_ENABLED=false` for the new revision. Its two creation routes return 503/Retry-After before order lookup, reservation or placement writes; authentication may still read account data. Public product reads and administrative remediation remain available. **Old binaries do not honor this new switch.** Do not wait for unrelated catalog/policy approval to request or carry out an independently authorized containment operation.
6. Keep sales ordering paused until the matching frontend/backend pair, genuine business/legal/catalog requirements and strict Production gate are complete. A containment deployment is not merchant readiness or permission to enable checkout.

## Verify and record without sensitive values

Record operator, date, source/image revision and a nonsecret change reference. Verify account revocation/disable, current-role authority, old-key/old-session rejection, external logging configuration and all relevant instances. Investigate old email-based order associations and historical simulated card submissions through the authorized incident process without exporting customer data into the repository. Review other credentials and rotate those shown to have been exposed; do not assume every development fallback was an actual live secret.

The new revision uses session versions and enabled-state checks, but global key rotation is still required: an exposed signing key can mint fresh tokens. No password-reset feature or automated incident remediation is claimed. Ordinary browser logout alone cannot revoke an attacker-held token.

Complete the exact deployment, migration, CORS and rollback steps in [RENDER_SECURITY_RUNBOOK.md](RENDER_SECURITY_RUNBOOK.md) and [the backend preparation guide](../../../Backend/docs/ORDER_SESSION_RELEASE_PREPARATION.md). Preserve the new key and additive schema during rollback; use only a reviewed compatible binary. If no compatible safe rollback exists, keep ordering isolated while repairing forward.
