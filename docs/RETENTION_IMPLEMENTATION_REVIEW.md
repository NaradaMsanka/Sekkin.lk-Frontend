## Provider capabilities are plan/account dependent

These are current published capabilities, **not the website's verified account settings**. Obtain dashboard/configuration evidence through the authorized operator without sending credentials or customer records into chat.

- **Supabase:** published daily-backup access is 7 days on Pro, 14 on Team and up to 30 on Enterprise; PITR is a separate option, and Free projects are directed to managed off-site exports. Database backups do not contain Storage API object bytes. An application's active rows do not age out merely because backup retention expires. [Supabase database-backup documentation](https://supabase.com/docs/guides/platform/backups).
- **Supabase location/access:** the selected project region covers the core database/backups, but operational/support/telemetry processing can occur elsewhere; the provider explicitly distinguishes those categories. Record the actual account region, subprocessors and support/transfer arrangements rather than promising all data remains in one country. [Supabase residency and transfers FAQ](https://supabase.com/legal/privacy-resources/data-residency-and-transfers-faq).
- **Render:** published service-log windows are Hobby 7 days, Pro 14 and Scale/Enterprise 30. Longer storage may use a separate logging provider. Service region is chosen in the dashboard; a public `onrender.com` address does not identify it. Capture actual runtime/request/deploy/audit log types separately. [Render logging](https://render.com/docs/logging), [Render regions](https://render.com/docs/regions).
- **Vercel:** published runtime-log retention is Hobby 1 hour, Pro 1 day and Enterprise 3 days; Observability Plus supplies a 30-day window on supported paid plans. Runtime/build/static-request logs are distinct; this project is a Vite SPA, and its browser console is not automatically an application server log. Check actual enabled integrations/drains and delivery metadata separately. [Vercel runtime-log types and limits](https://vercel.com/docs/logs/runtime).
- **Cloudinary:** automatic asset backup must be enabled and is not a guaranteed 30-day setting; own backup storage is a paid capability. Original/derived/CDN copies and backed-up versions have separate deletion considerations. The local cleanup requests CDN invalidation for managed images, but does not establish that backup versions were erased. Verify the product environment, backup configuration and any support-assisted deletion. [Cloudinary backup/version controls](https://cloudinary.com/documentation/backups_and_version_management), [asset deletion and cache invalidation](https://cloudinary.com/documentation/deleting_assets_tutorial).
- **Cloudinary location:** alternate EU/AP account endpoints are an Enterprise arrangement; published defaults or this code's API base are not proof of the current contracted account processing/backup/CDN locations. Obtain the actual product-environment and agreement evidence. [Cloudinary data-centre documentation](https://cloudinary.com/documentation/admin_api).

## Feasible manual access, correction and deletion procedure

This is a proposed operator procedure for the already approved request channel; **no production deletion is executed or authorized by this document**. It requires an authorized case decision and reviewed tools. There is no new self-service endpoint, automatic purge promise or account-deletion API in this patch.

1. **Register and verify:** assign a restricted case reference/authorized administrator, acknowledge through support and record the received date/30-calendar-day response aim. Verify control using proportionate existing account/order information and a trusted contact channel. Never request passwords, JWTs, raw card data or identity documents in ordinary chat. A guest's submitted email or an order ID alone is insufficient proof of authority over an account/order.
2. **Scope and holds:** identify the precise access/correction/deletion request and affected account, guest orders, reviews, cart/wishlist, support attachments/exports, logs and service-provider copies. Record necessary legal/fulfilment/refund/dispute/security holds and explain partial retention. Do not impose a guessed statutory deadline or erase accounting records merely to satisfy a blanket deletion request.
3. **Access/correction:** prepare a minimized export for the verified customer through an approved secure channel; exclude password hashes, tokens, request capabilities, other customers and private staff/security data. Verify each requested correction. Do not alter historical prices, delivery fees, quantities, collection evidence or financial status as an incidental profile correction. There is no inspected general profile-update/export API, so the operator must use an explicitly reviewed manual tool or separately scoped implementation.
4. **Contain authentication when needed:** the existing authorized account-disable/session-revoke actions can stop further authenticated use after the proper case decision. Disabled is not deleted. Browser-held token/profile/retry data can be cleared on the customer's own device; server revocation does not remotely remove browser storage. Do not enable an account solely to execute a privacy request.
5. **Rehearse the exact record plan in isolated PostgreSQL:** inspect actual foreign keys, nullability, triggers, uniqueness, row counts and access rights against the reviewed source. `reviews.user_id` and `wishlist_items.user_id` are non-null model references; `carts.user_id` also references users. `orders.user_id` is nullable in the model, while order customer contact fields are stored separately. Deleting a user first can fail or cause unintended effects under deployed constraints. Cart items are child records with orphan removal; order items are children of orders with cascade/orphan removal. Do not delete an order to remove a user. Resolve eligible cart/wishlist/review records and retained-order linkage/contact treatment explicitly before any user-row operation. If a review is retained, its author reference and any identifying text need a reviewed anonymization design; one does not exist merely because its public author label says Customer.
6. **Preserve required transaction integrity:** retain required order IDs, line quantities/prices, saved delivery/total/discount, state and acceptance/COD evidence under their approved retention/holds. Review operator identities/evidence references for minimization without destroying required accountability. Request-key hashes/fingerprints are part of durable duplicate-order protection; indiscriminate expiry/removal can allow a historical retry to create another order. A reviewed retry-window/tombstone design is required before pruning them. Changing account email or detaching a retained order also requires ownership/replay tests; neither is an automatic erasure shortcut.
7. **Execute only a separately approved narrow plan:** use the reviewed tool/transaction with preconditions, expected affected counts and rollback checks; record only nonsecret case/reviewer/action/count evidence. Do not run guessed bulk SQL, disable foreign keys, delete the Supabase project, rewrite old ownership or copy production data into the repository. If no safe supported tool exists, record the limitation and implement/review it before promising completion.
8. **Handle backups and downstream copies:** remove eligible active/support copies, request applicable provider/cache cleanup, and restrict residual backups until their verified lifecycle expires. Keep a restricted minimal deletion/hold ledger so an authorized restore can reapply completed deletions before exposing restored data. This ledger is a procedure requirement, not a newly implemented table/job. Do not promise immediate per-person erasure from immutable backups or a 30-day maximum unless the actual configuration supports it.
9. **Verify and communicate:** confirm no eligible personal data remains in the intended active views; verify old sessions fail and retained orders/totals/audit/retry rules still work. Explain completed actions, retained categories/reasons and known backup limitations through the verified channel within the approved response aim, or send a progress update. Retain only the minimum case evidence under the reviewed support/hold schedule.
